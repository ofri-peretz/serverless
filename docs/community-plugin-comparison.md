### Summary of value-add over the community plugin

The honest answer to "what do we add?":

1. **The `sls caching disable` command** — only documented offboarding path; the actual ghost-billing fix
2. **Three more `sls caching` commands** (`status`, `flush`, `preview`) for operational control without the AWS console
3. **A `before:remove:remove` hook** as defense-in-depth (the happy path doesn't need it, but edge cases might)
4. **TypeScript types throughout** + `flushOnDeploy` + per-endpoint CloudWatch override
5. **Stricter config validation** — enums for cluster size, TTL ranges
6. **Code-quality differences**: zero deps, no prototype pollution, jittered backoff, active maintenance

The honest answer to "what's NOT a differentiator?":

1. `sls remove` cleanup — CFN handles cluster teardown for both plugins
2. JSON-schema config validation existence — both have it; we have stricter rules
3. Shared API Gateway support — both have full support
4. ANY-method GET-only caching — both have the same disable-pattern logic
5. Most caching basics (enable/disable/size/TTL/encryption/per-key invalidation/cache keys)

### Summary of value-add (IAM) over the community plugin

What's clearly different:

1. **Four CLI commands** the community plugin lacks — `preview`, `audit`, `validate`, `status` — most-asked feature in the community plugin's open issues
2. **Two new auto-permissions** — EventBridge `PutEvents` and S3 `GetObject` — eliminates the most common copy-paste in `iamRoleStatements`
3. **`statementTemplates` + `iamManagedPolicies`** — share base policies and attach managed policies declaratively
4. **`suppressGlobalRole` + `requirePerFunctionRoles`** — opt-in least-privilege enforcement
5. **Strict statement validator** — Effect enum, Action format, Sid format
6. **Exported TypeScript config types** for `serverless.ts` users
7. **Zero runtime deps + active maintenance** (community last shipped 2021-05-21)

What's NOT a differentiator:

1. The `iamRoleStatements` config key, schema, and per-function role generation work identically — drop-in replacement
2. SQS / streams / DLQ auto-permissions — same set of actions in both
3. Permissions-boundary handling — same precedence rules
4. Role logical IDs (`<NormalizedFunctionName>IamRoleLambdaExecution`) — stable across the migration, no CFN role recreation
